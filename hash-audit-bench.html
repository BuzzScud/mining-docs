Where the constants come from

SHA‑256 starts from 72 fixed 32‑bit numbers. They are not arbitrary and they are not secret — they are derived from the square and cube roots of the small primes, precisely so that nobody can claim a hidden trapdoor was baked in. This is called a nothing‑up‑my‑sleeve construction.

H[i] = floor( frac( sqrt(p[i]) ) × 2^32 ) for the first 8 primes 2,3,5,7,11,13,17,19 K[t] = floor( frac( cbrt(p[t]) ) × 2^32 ) for the first 64 primes 2 … 311 frac(x) = x - floor(x) — keep only what is after the decimal point
Derivation, recomputed in this page from the primes

If any of these numbers were chosen freely, the designer could have searched for a value that creates a weakness only they know about. Deriving them from √2, √3, √5… removes that freedom: there is essentially nothing to choose.

02

Pad the message to a multiple of 512 bits

SHA‑256 only eats 512‑bit (64‑byte) blocks, so the message is extended. Append a single 1 bit, then as many 0 bits as needed, then the original length as a 64‑bit big‑endian integer. The length is appended so that two different messages can never pad to the same thing.

L = message length in bits k = smallest k ≥ 0 such that (L + 1 + k + 64) mod 512 = 0 padded = message ∥ 0x80 ∥ 0x00 × (k-7)/8 ∥ uint64_be(L)

03

Expand each block into a 64‑word message schedule

The 64‑byte block is read as sixteen 32‑bit words W[0..15]. The remaining 48 words are generated from them, so that every input bit gets stirred into many rounds rather than touching just one.

σ0(x) = ROTR⁷(x) ⊕ ROTR¹⁸(x) ⊕ SHR³(x) σ1(x) = ROTR¹⁷(x) ⊕ ROTR¹⁹(x) ⊕ SHR¹⁰(x) W[t] = W[t-16] + σ0(W[t-15]) + W[t-7] + σ1(W[t-2]) mod 2³² for t = 16 … 63 ROTRⁿ rotates bits right (they wrap around); SHRⁿ shifts right (they fall off).
04

Run 64 rounds of compression

Eight working variables a…h start from the current hash value. Each round mixes in one schedule word and one constant, then shifts everything down by one position. Click any row to expand the full arithmetic for that round.

Σ0(a) = ROTR²(a) ⊕ ROTR¹³(a) ⊕ ROTR²²(a) Σ1(e) = ROTR⁶(e) ⊕ ROTR¹¹(e) ⊕ ROTR²⁵(e) Ch(e,f,g) = (e ∧ f) ⊕ (¬e ∧ g) e chooses: f where e is 1, g where e is 0 Maj(a,b,c) = (a∧b) ⊕ (a∧c) ⊕ (b∧c) majority vote, bit by bit T1 = h + Σ1(e) + Ch(e,f,g) + K[t] + W[t] mod 2³² T2 = Σ0(a) + Maj(a,b,c) mod 2³² h=g g=f f=e e=d+T1 d=c c=b b=a a=T1+T2 mod 2³²

Why it is hard to reverse. Every round throws information away — the additions are mod 2³², so carries fall off the end and are gone. Running the rounds backwards would need those lost bits. Forwards is cheap; backwards is a search.

05

Add the working variables back into the hash value

This final addition is what makes the compression function one‑way rather than a reversible permutation. It is called the Davies–Meyer feed‑forward.

H[i] = H[i] + working[i] mod 2³², for i = 0 … 7
06

Bitcoin hashes twice

Bitcoin never uses a bare SHA‑256. Everything — block headers, transaction ids, merkle nodes — is SHA256(SHA256(x)). The second pass takes the 32‑byte digest as its input, pads it to one 64‑byte block, and compresses again.

SHA256d(x) = SHA256( SHA256(x) )
pass 1
pass 2

The stated reason is defence against length‑extension. SHA‑256 is a Merkle–Damgård construction: its output is its internal state, so given H(secret ∥ msg) you can keep hashing from there and produce H(secret ∥ msg ∥ pad ∥ extra) without knowing the secret. Hashing the digest a second time hides that state. Keccak, on the Monero tab, is immune by construction — it keeps 512 bits of its state permanently hidden.

Bitcoin serialises hashes little‑endian internally but block explorers print them big‑endian. Same 32 bytes, printed in the opposite order. This trips up nearly everyone once.

The avalanche property

Flip one bit of the input and roughly half the output bits should change — around 128 of 256. This is not a security guarantee on its own; it is the visible symptom of a hash that behaves like a random function. Click any input bit to flip it.

The nonce is the only thing a miner is really free to change, and it is only 32 bits — about 4.3 billion tries, which modern hardware exhausts in well under a second. Mining is not clever: it is this exact computation, repeated.

Two different hashes, two different jobs

Monero uses two unrelated functions and they are constantly confused for each other. Only one of them is a hash in the sense of the Bitcoin tab.

Keccak-256 — identity

Transaction hashes, block hashes, key derivation, the cn_fast_hash used all over the codebase. A normal cryptographic hash. Fully computed on this page.

auditable here
RandomX — proof of work

Since Nov 2019. Not a hash function at all: it is a virtual machine that compiles random programs and runs them against a 2 GB dataset, specifically so that a CPU beats an ASIC.

diagrammed, not computed — step 06

Keccak won the SHA‑3 competition in 2012, but Monero (and Ethereum) shipped the original Keccak before NIST changed the padding byte for the final standard. So Monero's “Keccak‑256” and NIST “SHA3‑256” give different digests for the same input. One byte of difference, shown in step 02.

01

The sponge, and your input

Keccak is not built like SHA‑256. There is no message schedule and no feed‑forward. There is a single 1600‑bit state, and you absorb the message into part of it and then squeeze the digest back out.

state b = 1600 bits, viewed as a 5 × 5 grid of 64-bit lanes A[x][y] rate r = 1088 bits (136 bytes) ← the part the message touches cap c = 512 bits ( 64 bytes) ← never touched, never output b = r + c output 256 bits, taken from the first 4 lanes after the last permutation

The capacity is the whole security argument. Those 512 bits are never written by the message and never read out. An attacker cannot see them or set them, which is exactly why Keccak has no length‑extension weakness — there is no way to resume the state from a digest.

02

Pad to a multiple of the rate

Keccak pads with a rule called pad10*1: a start byte, zeros, and a final 0x80 (the high bit) on the last byte of the block. Unlike SHA‑256 the message length is not appended — the padding rule alone makes it unambiguous.

padlen = 136 - (len mod 136) always at least 1, never 0 padded = message ∥ D ∥ 0x00 × (padlen-2) ∥ 0x80 D = 0x01 original Keccak — Monero, Ethereum D = 0x06 NIST SHA-3 — adds the domain-separation bits 01 when padlen = 1 the two collapse into one byte: D | 0x80

03

Absorb — XOR the block into the state

Each 136‑byte block is read as 17 little‑endian 64‑bit lanes and XORed into the first 17 cells of the 5×5 grid. The last 8 cells — the capacity — are left alone.

A[i mod 5][i div 5] ⊕= uint64_le( block[8i … 8i+7] ) for i = 0 … 16 lane index runs down columns: i = x + 5y
State after absorb, before permutation — 25 lanes of 64 bits
04

Permute — 24 rounds of θ ρ π χ ι

Five steps, each doing one job. Together they scramble all 1600 bits. Drag the round slider and watch the lanes change.

θ C[x] = A[x][0] ⊕ A[x][1] ⊕ A[x][2] ⊕ A[x][3] ⊕ A[x][4] D[x] = C[x-1] ⊕ ROTL¹( C[x+1] ) A[x][y] ⊕= D[x] diffusion — every lane now depends on two whole neighbouring columns ρ A[x][y] = ROTL^r[x][y]( A[x][y] ) rotate each lane by a fixed offset, so bits move along the 64-bit axis π B[y][2x+3y mod 5] = A[x][y] permute lane positions — breaks up the column structure θ just created χ A[x][y] = B[x][y] ⊕ ( ¬B[x+1][y] ∧ B[x+2][y] ) the only non-linear step. Without it the whole permutation would be solvable linear algebra. ι A[0][0] ⊕= RC[round] break the symmetry, so all-zero and all-one states do not stay symmetric

05

Squeeze out the digest

After the last permutation, read the first 256 bits of the state as little‑endian bytes. For a 256‑bit output that is just the first four lanes — no second permutation needed, because 256 is well under the 1088‑bit rate.

digest

Monero calls this cn_fast_hash. A transaction id is this function applied to the transaction's serialised prefix; a block id is this function applied to the block header (with the tree root and tx count), not to the RandomX result.

06

RandomX — why the proof of work is not computable here

RandomX is a full virtual machine. Hashing one candidate block means generating a random program from the block, allocating gigabytes, and executing millions of instructions. A browser page can honestly diagram it; it cannot honestly run it, and anything that claimed to would be faking.

seed
Block header + nonce
Blake2b hashes it down to a 256-bit seed. Change the nonce, get a completely different program.
↓
expand
Cache → Dataset  256 MB → 2080 MB
Argon2d builds a 256 MB cache, then SuperscalarHash expands it to a 2 GB dataset. Full nodes keep the cache and verify slowly; miners hold the whole dataset in RAM.
↓
compile
Generate a random program  256 instructions
Integer, floating-point and branch instructions over 8 integer registers, 4 FP registers and a 2 MB scratchpad — deliberately shaped like real CPU code so a general-purpose CPU has no handicap.
↓
execute
Run it  8 programs × 2048 iterations
Each program's result seeds the next. Roughly 16 million instructions and constant random reads against the 2 GB dataset per single hash.
↓
finalise
Blake2b of the final register file
Produces the 256-bit result that gets compared against the difficulty target — the same comparison as the Bitcoin tab.
Why the design is this hostile

An ASIC wins when the work is a small fixed circuit run billions of times — which is exactly what SHA‑256 is. RandomX makes the work a different program every time, needing branch prediction, out-of-order execution, floating point and 2 GB of fast RAM. Building a chip for that gets you approximately a CPU. Monero has also hard-forked its proof of work several times specifically to destroy any ASIC that did appear.

Bitcoin
2 SHA-256 blocks per try. Kilobytes of state. Perfect ASIC target.
Monero
~16M instructions + 2 GB RAM per try. Hostile ASIC target.

Same final test: is the result, as a big integer, below the target?
